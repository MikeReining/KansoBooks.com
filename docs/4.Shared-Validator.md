# KansoBooks Shared Validator

**Status:** Canonical / Binding

## Purpose

Define one validator core for import, review, export, and runtime preflight.

The validator answers:

- is this state valid?
- what findings exist?
- which rules were violated?
- which workflow is blocked?

## Core Decision

The validator is a pure function over normalized state plus contracts.

Allowed differences between callers:

- output formatting
- UI grouping
- exit/result mapping

Forbidden differences:

- rule ownership
- money parsing semantics
- match status semantics
- evidence-policy semantics
- export readiness semantics
- provider output schema semantics

## Input / Output

Conceptual API:

```rust
pub fn validate_project_state(
    input: ValidationInput,
    contracts: &'static ContractRegistry,
) -> ValidationResult
```

Output:

```rust
pub struct ValidationResult {
    pub normalized: Option<NormalizedProjectState>,
    pub findings: Vec<ValidationFinding>,
}
```

Rules:

- accumulate all independently knowable findings
- deterministic ordering
- no network calls
- no filesystem I/O
- no provider calls
- no database writes

## Pipeline

### Stage A - Parse / Load

Input adapters parse:

- CSV rows
- PDF/text extraction candidates
- provider JSON
- stored SQLite rows
- review decisions

Parser findings become `ValidationFinding` values with parser/contract rule IDs.

### Stage B - Normalize

Normalize into:

- typed money
- canonical dates
- source lineage
- normalized vendors
- accepted evidence candidates
- match candidates
- active evidence policy
- policy evaluations
- review decision timeline
- export request state

Normalization is best-effort so later independent findings can still surface.

### Stage C - Validate

Run contract-owned rule families:

- money
- source files
- bank transactions
- documents/evidence
- matching/confidence
- evidence policy
- review decisions
- audit events
- provider payloads
- **accounts** (CoA completeness, duplicate IDs, type/normal-balance
  consistency, system-account presence)
- **posting** (Σ debits = Σ credits per entry, `triggered_by_decision`
  present, account IDs exist, transfer/card-payment rules)
- **adjustment** (kind in v1 set, depreciation math, auto-reverse date
  present for timing adjustments, permanent-reclass has no auto-reverse)
- **reconciliation** (expected closing formula, difference → `Tied` or
  `AcceptedWithDifference`, no silent plug)
- **close gate** (all nine conditions evaluated; any unmet condition emits
  `close_gate.condition_not_met` with the specific condition named)
- **report** (trace-chain walkable for every report line, trial balance
  balances, re-export determinism)
- export readiness

### Stage D - Sort / Return

Finding order:

1. source/import
2. money/date parsing
3. bank transactions
4. documents/evidence
5. matching
6. evidence policy
7. review/audit
8. provider
9. accounts / CoA
10. posting / journal
11. adjustment
12. reconciliation
13. close gate
14. report / export
15. project-level structural findings

Within location, sort by `rule_id`.

## Rule Families

### Money

Validate:

- no float paths
- currency present
- parse success
- sign/direction consistency
- currency compatibility for arithmetic/export

### Source Files

Validate:

- checksum
- media type support
- duplicate source policy
- import batch membership

### Bank Transactions

Validate:

- required date/amount/description
- row lineage
- stable transaction ID inputs
- duplicate pressure within batch

### Documents / Evidence

Validate:

- extraction schema
- total amount
- date
- merchant
- source lineage
- confidence thresholds

### Matching

Validate:

- candidate references exist
- confidence factors explain score
- ambiguous candidates require review
- missing evidence remains visible as fact
- duplicates are not silently resolved

### Evidence Policy

Validate:

- active policy exists
- preset is known
- policy evaluation references an existing transaction
- requirement/severity combination is valid
- certainty gradient is valid for requirement/severity/finding state
- missing required evidence emits review-required finding
- missing optional evidence remains informational or ignored
- policy result has reason factors
- low/blocked confidence has visible reasons
- evidence class is not treated as accounting category

### Review

Validate:

- decision subject exists
- transition is allowed
- superseded decision exists
- action writes audit event

### Provider

Validate:

- provider output matches generated schema
- data-boundary policy is known
- cloud consent required when applicable

### Accounts

Validate:

- no duplicate account IDs
- `normal_balance` is consistent with `type`
- every `parent_id` references an existing account
- system accounts required by posting rules are present
- no account referenced by a posted entry is absent or deleted
- `capitalize_threshold` is present on accounts that drive
  `capitalize_and_depreciate` detection

### Posting

Validate:

- every `JournalEntry` satisfies Σ debits = Σ credits (rule
  `posting.debits_must_equal_credits`)
- every entry carries `triggered_by_decision`
- every account referenced in `lines` exists in the CoA
- transfer entries reference exactly two `asset.bank` or one `asset.bank` +
  one `liability.credit_card` account
- credit-card payment entries do not credit an expense account

### Adjustment

Validate:

- `kind` is in the v1 `AdjustmentKind` enum
- timing-difference adjustments have a non-null `auto_reverse` date
- permanent-reclassification adjustments (`owner_draw_reclass`,
  `capitalize_and_depreciate`) have `auto_reverse = null`
- `capitalize_and_depreciate` carries `useful_life_years`, `method`, and
  `half_year_convention`; the posted depreciation amount matches the
  declared method math (rule `adjustment.depreciation_math_mismatch`)

### Reconciliation

Validate:

- `expected_closing = opening_balance + Σ posted inflows − Σ posted outflows`
- `difference = expected_closing − statement_closing`
- `status = Tied` iff `difference.minor_units == 0`
- `status = AcceptedWithDifference` requires a non-null
  `accept_difference_decision_id` with a reason in the decisions log
- any account with `status = Difference` emits
  `reconciliation.difference_blocks_close`

### Close Gate

Validate each of the nine conditions per `Docs/AccountingModel.md`.
Each unmet condition emits `close_gate.condition_not_met` with the specific
condition ID. All nine must pass before `PeriodStatus` may be set to `Closed`.
The validator must be the single point that evaluates the gate; runtime must
not separately re-implement the conditions.

### Export

Validate:

- export spec exists
- fatal findings block export
- unresolved review state is represented
- active policy and policy version are included
- output claims have lineage or decision support
- every report line traces to a posted journal entry (rule
  `report.trace_chain_broken`)
- trial balance Σ debit = Σ credit (rule
  `close_gate.trial_balance_does_not_balance`)
- audit-package sha256 manifest matches actual artifact bytes

## Runtime Relation

Runtime may re-enforce contract rules, but the validator must be able to emit
the same `rule_id` for any statically knowable violation.

## Help / Doctor Relation

Validator findings are inputs to generated help and doctor recovery.

Rules:

- every emitted `rule_id` has contract-owned explanation/recovery metadata
- validator examples feed the validator-backed example registry
- doctor output may cite validator findings and traces, but must not invent
  explanations beyond rule/recovery bindings

## Definition of Done

The validator foundation is ready when import, review, export, and provider
payload checks all call one contract-driven validation core.
