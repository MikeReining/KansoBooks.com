# KansoBooks Contract Testing and Parity

**Status:** Canonical / Binding

## Purpose

Make drift between contracts, validator, runtime, generated outputs, GUI, and
exports a failing check.

## Core Decision

Financial correctness is enforced by tests, not team memory.

If a rule exists, it needs proof.

## Test Families

### Contract Completeness

Fail if:

- a live match status lacks contract definition
- an evidence-policy preset/result lacks contract definition
- a rule ID lacks a `RuleBinding`
- an export spec lacks readiness rules
- a provider schema lacks validation
- a GUI raw payload lacks generated type ownership
- an `AdjustmentKind` variant is used in the engine that is not in the
  contract enum (enforced by exhaustive match)
- a `CloseGateCondition` variant is evaluated in the engine that is not in
  the contract enum
- a report projection function is missing from `report.rs` for a v1 report
  type
- a new `AuditEventKind` is used without a `RuleBinding`
- a served MCP/Kanso Interface tool lacks a descriptor
- a descriptor appears in the manifest but has no implementation
- a contract-known MCP error lacks a stable `rule_id`
- an advertised memory kind lacks a contract definition
- a CLI command or MCP tool lacks generated help metadata
- a reachable rule lacks generated explanation/recovery metadata
- a public or prompt example is not backed by a validator-approved recipe

### Validator Coverage

Required:

- valid examples pass
- invalid examples fail with expected `rule_id`
- money parsing rejects float paths
- unsupported CSV fixtures produce findings
- provider output schema violations are caught
- ambiguous/missing/duplicate match cases are covered
- missing evidence optional under Lean is not treated as review-required
- missing evidence required under Strict is treated as review-required

### Runtime Parity

For every runtime-enforced contract rule:

- validator can emit same `rule_id`
- runtime error carries same `rule_id` when applicable
- a fixture exercises both paths where practical

### Kanso Interface / MCP Conformance

Required:

- contract-owned interface registry exists for every served tool
- implementation cannot serve a tool missing from the registry
- registry cannot list a tool without implementation or explicit unavailable
  stub
- manifest, `list_tools`, `explain_tool`, schemas, public examples, and
  skill-pack requirements are generated/proven from the registry
- CLI help, MCP help, doctor recovery, prompt fragments, and examples are
  generated/proven from the same contract registry and rule bindings
- removed or deprecated features update registry lifecycle metadata and stop
  serving stale tools and stale help/recovery surfaces
- new semantic capabilities include Kanso Interface impact: descriptors,
  manifest, errors, dry-run/simulation, grants, conformance, public spec, and
  Eve/skill-pack behavior, or an explicit non-exposure reason
- stdio MCP client harness can connect to the local server
- `kanso.get_mcp_manifest` is schema-valid and generated from descriptors
- `kanso.list_tools` and `kanso.explain_tool` match manifest projections
- `kanso.get_help_manifest`, `kanso.get_help_topic`, and `kanso.explain_rule`
  match generated help artifacts
- every tool returns the uniform success/error envelope
- every contract-known failure carries `rule_id`
- runtime-only failures use stable runtime codes and remain runtime-owned
- read tools return byte-identical JSON to equivalent CLI/proof outputs on
  the same fixture
- propose tools write only `AgentProposal` records
- accepted proposals write `ReviewDecision` records through Kanso review paths
- forbidden writes to compiled truth paths are structurally rejected
- `kanso.dry_run_proposal` matches the corresponding propose tool output
  except durable IDs, timestamps, state-transition fields, and writes
- `kanso.simulate_close` matches close preflight blockers and writes no close,
  report, package, ledger, decision, or evidence artifact
- doctor tools cite rule IDs/findings/remediation and do not invent
  explanations
- prompt fragments cite generated help/recovery bindings and do not invent
  schema fields, tools, permissions, or rule IDs
- examples rendered in public docs, CLI help, MCP help, and prompt fragments
  come from validator-backed recipes
- `kanso mcp doctor` detects broken client setup, invalid folder, missing
  grant, and missing evidence-content consent with structured errors
- `kanso mcp conformance --client <...>` passes against the reference server
- memory tests run if memory is advertised: scope violation, cross-folder
  rejection, cross-period grant requirement, expiry at close, audit events,
  and prompt-injection fixture

### Posting and Accounting Tests

Required:

- standard inflow/outflow posts correct debit/credit pair per fixture
- transfer between two bank accounts posts as zero-net entry, not income
- credit-card payment posts bank → liability, not expense
- personal expense produces no journal entry
- refund posts reversal to original expense account
- `capitalize_and_depreciate` straight-line with half-year: math verified
  against expected amounts in golden fixture
- `capitalize_and_depreciate` declining-balance: math verified
- auto-reversal fires on the named date as its own entry; original entry
  is unchanged
- trial balance balances on every closed-period fixture
- period cannot be closed while any close-gate condition is unmet (each
  of the nine conditions has a fixture that blocks on it)
- report projected from the same journal produces byte-identical output on
  two separate runs (determinism)
- income statement A = L + E check on balance-sheet fixture
- trace-chain walker succeeds for every report line on closed-period fixture
- trace-chain walker fails (emits `report.trace_chain_broken`) when a
  journal entry's `triggered_by_decision` references a missing decision

### Reconciliation Tests

Required:

- account with no difference is `Tied`
- account with difference and no `accept_difference` decision blocks close
- account with difference and valid `accept_difference` decision is
  `AcceptedWithDifference`; close proceeds
- `accept_difference` without a reason is rejected by the validator

### Export Tests

Required:

- clean CSV export snapshot
- review report snapshot
- audit log export snapshot
- income statement snapshot from closed-period fixture
- balance sheet snapshot; A = L + E holds
- trial balance snapshot; Σ debit = Σ credit holds
- general ledger snapshot; running balances match
- audit-package sha256 manifest is correct
- re-export of same closed state → byte-identical artifacts
- fatal finding blocks export
- unresolved review item is represented honestly
- active evidence policy and version are included
- export metadata includes contract version/source batch

### Generated Artifact Currency

CI should run:

- Rust-to-TS binding check
- JSON schema check
- prompt block check
- export spec check
- Kanso Interface registry/manifest check
- generated help docs check
- generated doctor/recovery metadata check
- generated prompt fragments check
- validator-backed examples check

Generated drift fails the build.

### Help And Recovery Parity

Required:

- every served CLI command has a `CommandDescriptor`
- every served MCP tool has a `ToolHelpDescriptor`
- every reachable `rule_id` has a `RuleExplanation`
- every recoverable failure has a `RecoveryHint`
- every safe exact fix has a `FixCommand`; unsafe or judgment-based fixes mark
  `requires_manual`
- every generated example names the rules and tools it exercises
- `kanso help --json` matches generated `help_kanso_cli_spec.md`
- `kanso explain rule <rule_id> --json` matches
  `help_rule_explain.json`
- `kanso explain tool <tool_name> --json` matches
  `help_tool_explain.json`
- `kanso doctor --json` and MCP doctor tools return the same recovery binding
  for the same failure
- `kanso dev export-contracts --check` fails when any help, doctor, prompt,
  example, schema, or MCP projection is stale

### GUI Boundary Tests

Required for non-trivial surfaces:

- presenter tests over fixtures
- every surface state renders
- views do not import raw contracts
- presenters do not import React/Tauri
- GUI statuses map from contract-owned states

## Fixture Strategy

V1 fixtures must include:

- clean bank CSV
- malformed amount
- missing date
- duplicate transaction
- matching receipt/evidence
- missing evidence
- missing evidence optional under Lean
- missing evidence required under Strict
- ambiguous receipt set
- suspicious refund/negative amount
- invalid provider JSON
- export with unresolved fatal finding
- transfer between two bank accounts (must not post as income/expense)
- credit-card payment (must not double-count as expense)
- personal expense (no journal entry)
- `capitalize_and_depreciate`: straight-line, useful life 5 years, half-year
  convention; golden debit/credit pairs
- `capitalize_and_depreciate`: declining-balance; golden debit/credit pairs
- at least one of each timing-difference adjustment kind with auto-reverse
- reconciliation: tied account
- reconciliation: account with unaccepted difference (blocks close)
- reconciliation: account with accepted difference (close proceeds)
- full close-period smoke: bank CSV + card CSV + receipts + one adjustment;
  IS/BS/GL/TB generated; trial balance balances; re-export byte-identical

Use real-looking data, but never real user financial data.

## Golden Outputs

Golden outputs protect trust:

- normalized transaction JSON
- match candidate JSON
- policy evaluation JSON
- validation findings
- clean CSV export
- review report
- audit log
- journal entry JSON for each standard posting kind
- income statement (full closed-period fixture)
- balance sheet (same fixture; A = L + E verified)
- trial balance (same fixture; Σ debit = Σ credit verified)
- general ledger (same fixture; running balances verified)
- reconciliation summary (same fixture)
- `capitalize_and_depreciate` debit/credit pairs (straight-line and
  declining-balance variants)

Golden updates require intent and review.

## No Legacy Parity Obligation

This is a new project.

Do not preserve old parked-project semantics, names, tests, or compatibility
paths unless a KansoBooks doc explicitly adopts them.

## Definition of Done

The parity wall is working when changing a contract without updating validator,
runtime, generated outputs, GUI, or exports fails locally and in CI.
