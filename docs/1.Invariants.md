# KansoBooks Validity Invariants

**Status:** Canonical / Binding

## Core Definition

A KansoBooks project state is valid iff every source file, extracted fact,
normalized transaction, match candidate, evidence-policy evaluation, review
decision, audit event, and export conforms to the Rust contract layer.

Every financial claim must be either:

- source-derived
- validator-derived
- user-approved
- exported from reviewed/validated state

## Two SSOTs

KansoBooks has two SSOTs that share one spine.

| SSOT | Owns |
|---|---|
| Product contract SSOT | Schemas, rule IDs, statuses, provider policies, exports, generated types, prompt schemas. |
| Financial truth SSOT | Money math, evidence lineage, review decisions, audit events, ledger invariants when ledger exists. |

The financial truth SSOT is expressed through the product contract SSOT and
enforced by validators/runtime.

## Locked Invariants

- Rust contracts are the semantic authority.
- No floats for money.
- Money is integer minor units plus currency.
- Source files are immutable inputs once imported; corrections create new state.
- Bank transactions are cash evidence, not category truth.
- Receipts/documents are evidence, not accounting truth.
- Missing evidence is objective fact, not automatic failure.
- Evidence requirements are policy-owned interpretation.
- Policy never changes facts; it changes severity and required action.
- AI output is proposal data, never accepted truth.
- User decisions are explicit truth for review outcomes.
- Every accepted claim links to source evidence or a user decision.
- Every user-visible status has a contract-owned meaning.
- Every validation finding has a stable `rule_id`.
- Every export is reproducible from stored state.
- Uncertainty is visible.
- Runtime may re-enforce rules but may not define static rules first.
- UI may summarize or group truth but may not reinterpret truth.
- UI must distinguish evidence availability from evidence requirement.
- Prompts may request schema-shaped output but may not define financial rules.
- Cloud/provider use requires explicit consent and visible data-boundary copy.
- Deletion requires explicit user intent and auditability.
- Ledger posting is active in v1 per `Docs/AccountingModel.md`. Debits MUST
  equal credits per journal entry before the entry can land in
  `ledger/<year>/journal.jsonl`.
- Posted ledger entries are immutable. Corrections are reversing or adjusting
  entries. No mutation of prior records.
- Every journal entry carries `triggered_by_decision` referencing the decision
  that produced it; trace chain MUST be walkable from report → entry →
  decision → transaction → evidence.
- Auto-reversing entries (year-end adjustments) fire on the named `auto_reverse`
  date as their own distinct entries; they do not mutate the original entry.
- Year-end adjustments are constrained to the v1 set defined in
  `Docs/AccountingModel.md`. New adjustment kinds are not invented at runtime
  or in the validator; they require a contract-level design pass.
- The close gate (`Docs/AccountingModel.md`) is the validator-owned definition
  of "books are ready." A period MUST NOT be marked `closed` unless all nine
  gate conditions hold.
- Reports (IS, BS, GL, TB) MUST be projected from the posted journal, not from
  raw transactions or AI suggestions. Any report number that cannot be traced
  back to a posted journal entry is a validator failure.
- The trial balance MUST satisfy Σ debits = Σ credits across all journal entries
  for the period before the close gate can pass condition 9.
- Reconciliation: a source account's computed expected closing balance MUST
  equal the statement's declared closing balance for the account to be
  reconciled. Differences are resolved by user-accepted `accept_difference`
  decisions, never by silent rounding or plug entries.

## Static vs Runtime Boundary

A failure is static if it can be known from source files plus contract data
without external state.

Static examples:

- invalid currency code
- amount cannot be parsed
- unsupported CSV profile
- duplicate source checksum in one batch
- missing required extraction field
- impossible match status transition
- impossible evidence-policy result
- missing required evidence under a policy that marks it review-required
- export requested with unresolved fatal findings
- AI/provider payload violates schema

A failure is runtime/environmental if it depends on external state.

Runtime examples:

- file disappeared
- file permissions changed
- provider unavailable
- API key missing
- SQLite write failed
- user denied cloud consent
- OCR timeout

If a static failure first appears at runtime, the contract/validator design is
incomplete.

## V1 Financial Boundary

v1 posts a cash-basis ledger per `Docs/AccountingModel.md`.

v1 enforces:

- money precision (no floats, integer minor units + ISO currency)
- source lineage and trace chain
- transaction completeness inside an import batch
- evidence extraction schema validity
- match status validity
- evidence-policy evaluation validity
- posting correctness (Σ debits = Σ credits per entry)
- close gate (nine conditions; journal balance is condition 9)
- review decision auditability
- export reproducibility (same inputs → byte-identical reports)
- audit-ready package integrity (sha256 manifest per artifact)

Double-entry rules are contract-owned in `Docs/AccountingModel.md` and
`Docs/1.Invariants.md`. Adjustments, reconciliation, and report projection
rules are also contract-owned. Runtime must not invent them.

## Preflight Obligations

Import/review/export preflight must:

- normalize input into contract-owned types
- evaluate against an explicit active evidence policy
- accumulate all independently knowable findings
- emit findings with `rule_id`, severity, location, and subject
- never approve state that export/runtime would reject for contract-known
  reasons

## Definition of Done

Foundation is valid when these invariants are enforced by contracts,
validators, runtime consumption, generated outputs, GUI boundaries, and tests.
