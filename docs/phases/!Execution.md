# Execution Playbook (`!Execution`)

Use this file together with exactly one authoritative phase, slice, or plan
document (the target doc, passed by `@` reference). This playbook is process
only. It does not duplicate technical scope. Do not edit this file to record
sprint progress. Sprint state belongs in the target doc.

This repo is `KansoBooks.com`: the public website, control-plane website
foundation, docs, and future Autonomous Content Engine. It is not the desktop
KansoBooks product repo.

Typical target docs:

- `docs/phases/FoundationSetup.md`
- `docs/phases/DeploySetup.md`
- `docs/phases/SupabaseControlPlane.md`
- `docs/phases/AutonomousContentEngine.md`
- future website/content-engine phase docs under `docs/phases/`

## Execution Modes

### Packet Mode

Use when the founder wants copy-paste work orders.

The PM reads this playbook plus one target doc and emits two fenced packets:

- Task 1: implementer
- Task 2: reviewer / closer

Packet Mode stops after emitting packets. It does not implement.

### Goal-Orchestrated Execution Mode

Use when the founder asks an AI orchestrator to run, lead, delegate, or execute
the target doc.

The lead agent owns sequencing, delegation, review routing, closeout, and
continuation. The lead may implement only when it explicitly assigns itself the
Task 1 lane for the current sprint.

Goal-Orchestrated Mode continues until the target doc is exhausted, a gate
fails after a bounded fix pass, or a human stop condition is hit.

## Task Lanes

These labels name who owns the work. They do not describe technical risk.

| Packet | Lane | Owner |
|---|---|---|
| Task 1 | AUTO | Coding/content agent implements one sprint. |
| Task 2 | KEEP | Reviewer/closer validates, updates target-doc status, and closes the sprint. |

In Goal-Orchestrated Mode, Task 2 may be a designated reviewer agent. It does
not have to be the founder.

Task 1 and Task 2 must remain logically separate even when the same system runs
both. A sprint is not closed because Task 1 says it is done.

## Repository Guardrails

All agents must preserve these repo boundaries.

## Codex Automation Safety Model

Skills are workflow instructions, not a security boundary.

Codex agents should execute only what their skills say, but the system must
still assume an agent with file, terminal, browser, or git tools can make a bad
edit, run the wrong command, leak a secret, or push unintended changes.

Therefore, autonomous content publishing must eventually use defense in depth:

- separate Codex automation roles for strategist, researcher, writer, reviewer,
  auditor, publisher, maintainer, and metrics roles
- smallest practical toolsets per role
- no `all` toolset for scheduled publishing roles
- separate OS user or working directory for Codex automations
- dedicated clone or worktree for content automation
- restricted credentials
- branch protection
- CI path guard for autopublish
- content validation before merge/deploy
- no direct access to Vercel, Supabase, Lemon Squeezy, DNS, or GitHub admin
  credentials unless a sprint explicitly requires that admin lane

Recommended future autopublish model:

1. Canonical website and content-engine code live in this repo.
2. Codex works in a dedicated content automation clone/worktree.
3. Codex may edit only approved content paths during autopublish.
4. CI rejects autopublish changes outside the allowlist.
5. CI runs content validation, typecheck, lint, and build.
6. Passing autopublish changes merge/deploy automatically.
7. Failures produce an exception report instead of asking the founder to edit.

Initial allowlist once content exists:

```text
content/**
public/content/**
public/og/**
docs/content-runs/**
```

Possible additional allowlist after explicit implementation:

```text
src/content/**
src/lib/content/**
scripts/content/**
```

Never allow scheduled content agents to mutate these without an explicit
non-content-engine sprint:

```text
src/app/api/**
src/lib/supabase/**
src/lib/control-plane/**
supabase/**
.env*
next.config.ts
package.json
package-lock.json
.github/**
```

Skills may be improved by Codex, but canonical skill changes should land
through a normal implementation/review sprint, not silent autopublish.

## Human Stop Conditions

Stop and ask the founder only when the decision changes product semantics,
trust semantics, security posture, or roadmap priority.

Stop for:

- product positioning conflict with canonical docs
- cloud data boundary ambiguity
- AI truth boundary ambiguity
- tax/legal/accounting advice uncertainty
- credentials, billing, or provider failure
- branch protection, CI, or deployment failure that cannot be mechanically fixed
- Codex automation access-policy changes
- deleting or rewriting large parts of the public website
- allowing autonomous agents broader write access than the current target doc
  authorizes

Do not stop for:

- routine topic choice inside an approved content plan
- routine article drafting
- routine metadata optimization
- routine internal link updates
- routine content refreshes
- routine publishing when all gates pass

## Goal-Orchestrated Run Brief

When using Goal-Orchestrated Mode, start with this concise brief:

```text
Goal-Orchestrated Run
Target doc:
Starting sprint:
Delegation plan:
Required checks:
Human stop conditions:
Next action:
```

Then begin the sprint loop. Do not ask the founder to relay Task 1 / Task 2
text unless delegation is unavailable.

## Sprint Loop

1. Pick the next sprint from the target doc.
2. Create or assign Task 1.
3. Run/delegate Task 1.
4. Inspect Task 1 handoff, diff, generated files, and checks.
5. Create or assign Task 2.
6. Run/delegate Task 2 review and closeout.
7. If Task 2 fails for a blocking defect, route a narrow fix back through Task
   1 for the same sprint.
8. If Task 2 passes, complete docs, checks, and commit/merge/deploy steps
   required by the target doc.
9. Continue to the next sprint.

After each sprint, report:

```text
Sprint <id>: PASS | FAIL | BLOCKED
Task 1:
Task 2:
Commands:
Docs updated:
Git:
Next:
```

## How To Pick The Next Sprint

1. Open the target doc.
2. Locate its authoritative ordering: numbered phases, sprint table, checklist,
   dependency column, or top-to-bottom section order.
3. Select the next item not marked done and not blocked by an unfinished
   dependency.
4. If multiple items are equally next, choose the smallest deliverable that
   unblocks the critical path.
5. If ordering is ambiguous, state the assumption in one sentence and proceed
   unless the choice changes product/security/trust semantics.

### Conversation-Anchored "Next"

In Packet Mode, when the founder asks only for "next" or "next sprint" in the
same chat after packets were already issued for the same target doc:

- advance from the last sprint this thread issued
- do not use git state to skip ahead or rewind unless the founder asks to
  realign with repo state
- if there is no successor, say the ordered plan is exhausted

In Goal-Orchestrated Mode:

- advance only after Task 2 PASS
- use the target doc as truth after resume
- reconcile stale thread memory to the target doc unless that changes scope

## Naming The Sprint

Use the target doc's native IDs in packet titles, commits, closeout notes, and
run logs. If the target doc has no IDs, derive a short stable ID from the
section name, such as `Phase 2 - Content Infrastructure`.

## Task 1 Responsibilities

Task 1 owns implementation for one sprint.

Task 1 must:

- read this playbook and the target doc
- read mandatory repo/product docs for the touched area
- implement only the current sprint
- preserve the website/product/content guardrails
- run focused checks
- leave a concise handoff for Task 2
- stop when implementation is reviewable

Task 1 must not:

- mark sprint checkboxes complete
- declare PASS
- archive target docs
- make sprint closeout commits unless the target doc explicitly merges lanes
- broaden Codex automation access or credentials outside sprint scope
- edit unrelated website areas
- change product truth to make content easier

## Task 2 Responsibilities

Task 2 owns review and closeout.

Task 2 must:

- inspect the diff
- verify against the target doc
- run or verify required checks
- classify issues as blocking defects or closeout hygiene
- fix closeout hygiene directly
- update target-doc status when PASS
- record commands run
- ensure commit/merge/deploy steps match the target doc
- route blocking defects back to Task 1

Task 2 must not fail a sprint solely for closeout hygiene it can safely fix.

Blocking defects include:

- product/trust/security boundary violation
- unsupported product claim
- tax/legal/accounting advice risk
- broken build or required check failure
- wrong sprint scope
- missing required validation
- autopublish path-guard failure
- content audit failure
- accidental edits outside authorized paths

Closeout hygiene includes:

- target-doc checkbox/status update
- shipped note
- run log update
- internal link bookkeeping
- generated sitemap or content index refresh
- formatting
- commit message cleanup

## Local Green Gates

### Checkpoint Commit

Use for coherent work-in-progress.

Required:

- focused check for touched files when practical
- no claim that the sprint passed

### Sprint Closeout Commit

Use when Task 2 marks a sprint PASS.

Required:

- target-doc `Done when` commands
- focused regression checks for touched files
- default local checks when shared website/content infrastructure changed

### Manual Git Handoff

Use only when the agent cannot complete the git action directly.

Required:

- any command block handed to the founder for staging, committing, pushing, or
  PR work must start with `cd /Users/mike/Documents/GitHub/KansoBooks.com`
- include the complete git sequence from that working directory
- do not assume the founder's shell is already in the repo

### Phase Or Release Close

Use when a full target doc, release, or archive closes.

Required:

```text
npm run typecheck
npm run lint
npm run build
```

Add content validation, link checks, browser checks, or deployment checks when
the target doc requires them or the sprint touches those surfaces.

Packet Mode replies must start with two consecutive fenced blocks and no prose
before the first fence.

First fence:

```text
# Task 1 - AUTO - Implementer (<sprint ID>)
Who runs this: coding/content agent
...
```

Second fence:

```text
# Task 2 - KEEP - Reviewer / closer (<same sprint ID>)

```

After the second fence, print exactly three short manager-orientation lines:

```text
Task 1 (<status>)
Task 2 (<status>)
After this sprint: N sprints left.
```

If `N = 0`, use:

```text
After this sprint: 0 sprints left - ordered plan exhausted.
```

Do not implement in Packet Mode unless the founder later asks you to wear the
implementer hat.

## Target Doc Closeout

When Task 2 closes the final ordered sprint in a target doc:

1. Ensure every open follow-up is closed, moved forward, or explicitly kept with
   a reason.
2. Move permanent truth into canonical docs, implementation, tests, scripts, or
   content schemas.
3. Add an archive banner to the target doc:

```text
Archived: YYYY-MM-DD
Status: Historical / Non-authoritative
Superseded by: <live/root paths>
Do not implement from this file.
Do not rely on this file for current execution.
Code, tests, schemas, and active canonical docs are the source of truth.
```

4. Move the file to `docs/archive/`, preserving enough path context in the
   filename when useful, such as `phases-AutonomousContentEngine.md`.
5. If the archived doc points to obsolete implementation, old agent setup, or
   stale process, keep only historical context there. Do not leave active
   instructions that a future agent might mistake for current work.

Do not archive:

- `docs/phases/!Execution.md`
- a still-open umbrella doc
- an active strategy doc that still governs future implementation

If a future `docs/phases/README.md` exists, update it during archive closeout.
If `docs/archive/README.md` exists, preserve its warning contract.

## Content Autopublish Closeout

Autopublish is allowed only after the target doc has explicitly created the
content infrastructure, validation gates, and path guard.

Until then:

- content-engine implementation may be autonomous
- content strategy docs may be autonomous
- real public content publishing is not assumed

Once autopublish exists, Task 2 must verify for each content sprint:

- allowed paths only
- content metadata complete
- no unsupported claims
- no tax/legal/audit advice
- internal links resolve
- external sources resolve where applicable
- sitemap/index updates
- typecheck, lint, build, and content validation pass
- deploy path is green or correctly queued

Founder approval is still not a gate when the autopublish gates pass.

## After You Respond

Packet Mode: stop after packets.

Goal-Orchestrated Mode: keep going until the target doc is exhausted, a gate
blocks progress, a human stop condition is hit, or the founder asks you to
pause.
