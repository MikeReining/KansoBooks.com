# Presenter, State, and Surface Briefs

**Status:** Canonical / Binding

## Purpose

Capture founder/product taste before UI code.

Every non-trivial surface needs:

- `brief.md`
- `state.ts`
- `presenter.ts`
- `fixtures.ts`
- presenter tests

## Surface Brief

Location:

```text
apps/desktop/src/surfaces/<surface-name>/brief.md
```

The brief is the authority for surface-specific taste.

It defines:

- purpose
- raw input
- required states
- presentation rules
- actions/interactions
- non-goals
- acceptance criteria

## Required Template

```markdown
# Surface: [Name]

**Purpose**
(one sentence)

**Raw Input**
- Command/event: `xxx` (type: `RawXxx`)

**Required Surface States**
- loading
- error
- empty
- filtered_empty
- ready

## Presentation Rules
- Visibility:
- Grouping:
- Noise policy:
- Humanization:
- Policy interpretation:
- Trust/evidence:
- Drill-down policy:
- Empty/error messaging:

## Actions / Interactions
- ...

## Non-Goals
- ...

## Acceptance Criteria
- [ ] Presenter tests pass
- [ ] All states render correctly
- [ ] Trust/evidence rules are visible
```

Do not invent alternate brief formats without updating this doc.

## Evidence Drawer Requirements

`apps/desktop/src/surfaces/evidence/brief.md` owns the Evidence Drawer taste
rules before Phase 4 implements the surface.

Presenter obligations:

- render one selected subject at a time: `EvidenceDoc`, `ExtractedDocument`,
  `MatchCandidate`, or `BankTransaction`
- expose source lineage, page range, provider/extraction method, and passive
  external links without fetching provider URLs
- show per-field confidence bands when present; no hidden AI/OCR trust
- keep edit affordances available on every extracted field, including
  high-confidence fields
- show decision history from append-only `ReviewDecision` and `AuditEvent`
  state; the view may show effective state but must not erase history
- preserve contract-owned match status language, including calm
  `AwaitingStatement` copy: "Waiting for statement."

Presenter non-goals:

- no confidence scoring
- no policy severity scoring
- no mutation of evidence, matches, or history
- no provider calls or network fetches
- no handwritten mirrors of raw backend payloads

## State Contract

`state.ts` defines the contract between controller/presenter and view.

Required:

- discriminated union
- all renderable states named
- curated view models only
- no raw backend payloads in view state unless explicitly a redacted raw detail
  object for inspection

Common states:

- `loading`
- `error`
- `empty`
- `filtered_empty`
- `ready`
- `permission_gated`
- `unsupported`

## `empty` vs `filtered_empty`

Use `empty` when raw source has no relevant data.

Use `filtered_empty` when raw data exists but presenter rules hide it.

Example:

- no transactions imported: `empty`
- only low-salience matched items hidden by current review filter:
  `filtered_empty`

## Presenter Contract

Presenter rules:

- pure
- deterministic
- local to one surface
- all taste rules traceable to `brief.md`
- fixture-testable without DOM, Tauri, network, or filesystem

Recommended shape:

```ts
export function presentReviewWorkbench(
  raw: RawReviewWorkbenchPayload,
): ReviewWorkbenchState
```

Presenter may own:

- issue ordering
- grouping
- badge text
- summary text
- confidence explanation display shape
- policy outcome display shape
- certainty gradient display shape
- drill-down package construction

Presenter may not own:

- financial status definitions
- confidence scoring
- policy requirement/severity scoring
- certainty gradient scoring
- validation rules
- provider consent policy
- export readiness

## Controller Contract

Controllers:

- call gateway
- use TanStack Query/shared helpers
- pass raw data to presenter
- return one surface-state value

Controllers must not:

- filter domain data
- group issues
- derive financial labels
- render JSX

## Fixture Contract

Each non-trivial surface has fixtures for:

- loading
- error
- empty
- filtered_empty when applicable
- ready
- noisy raw data proving presenter rules

Do not import fixtures into production views.

## Build Order Per Surface

1. write `brief.md`
2. define `state.ts`
3. create raw and state fixtures
4. implement `presenter.ts`
5. write presenter tests
6. implement `gateway.ts`
7. implement `controller.ts`
8. implement `view.tsx`
9. write render tests
10. integrate into shell

## Definition of Done

Surface behavior is valid when product taste is durable in `brief.md`, pure in
`presenter.ts`, explicit in `state.ts`, and visually rendered without creating
new financial truth.
