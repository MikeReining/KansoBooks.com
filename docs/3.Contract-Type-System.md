# KansoBooks Contract Type System

**Status:** Canonical / Binding
**Authority:** Subordinate to `Docs/Naming.md` for type names. The
work-unit type is `BooksPeriod`; `ReportOutput` is the family for
generated outputs. The Kanso Interface / MCP coworker surface adds `AgentProposal`,
`AgentPolicy`, `McpToolDescriptor`, `McpManifest`, `KansoMcpError`, and
`AgentMemory` types per `Docs/MCPSurfaceModel.md`. Help and recovery add
`HelpTopic`, `RuleExplanation`, `RecoveryHint`, `FixCommand`,
`ExampleRecipe`, `PromptFragment`, and `HelpArtifactManifest` per
`Docs/HelpAndRecoveryModel.md`.

## Purpose

Define the concrete Rust ownership model for KansoBooks contract truth.

This document fixes:

- module ownership
- core types
- registry layout
- rule binding shape
- generated output boundaries

server adapter; semantics stay in contracts and core.

## BooksPeriod Type

(Replaces the legacy `Report` work-unit struct per `Docs/Naming.md`.)

```rust
pub struct BooksPeriod {
    pub id: BooksPeriodId,
    pub display_name: String,
    pub base_currency: Option<CurrencyCode>,
    pub connected_expenses_folder: Option<String>,
    pub connected_statements_folder: Option<String>,
    pub extraction_strategy: Option<ExtractionStrategy>,
    pub status: BooksPeriodStatus,
    pub created_at: String,
}

pub enum BooksPeriodStatus {
    Draft,
    InReview,
    ReadyToClose,
    Closed,
    Reopened,
}

pub enum ExtractionStrategy {
    SinglePrimary,
    Ensemble,
}
```

Rules:

- `base_currency` is `None` at creation; set lazily on first statement
  import (audit `books_period.base_currency_inferred`)
- if set later, prior amounts keep their original currencies
- ingestion is always scoped to exactly one active `BooksPeriod`
- `status` follows the lifecycle in `Docs/BooksPeriod.md`; transition to
  `Closed` requires the close-gate evaluator to pass; agents MUST NOT
  drive `status` transitions in v1

## AgentProposal Type

(Per `Docs/MCPSurfaceModel.md`. Lives in `proposals/<year>.jsonl`,
append-only.)

```rust
pub struct AgentProposal {
    pub id: AgentProposalId,
    pub books_period_id: BooksPeriodId,
    pub session_id: AgentSessionId,
    pub agent_client: AgentClient,
    pub created_by_agent_label: String,
    pub proposal_kind: ProposalKind,
    pub subject: ProposalSubject,
    pub payload: ProposalPayload,
    pub citations: Vec<Citation>,
    pub validation_result: ValidationResult,
    pub journal_projection: Option<JournalProjection>,
    pub disposition_rule: DispositionRule,
    pub state: ProposalState,
    pub from_proposal: Option<AgentProposalId>,
    pub created_at: String,
}

pub enum ProposalKind {
    ChangeCategory,
    PairTransfer,
    MarkPersonal,
    AttachEvidence,
    PostTransaction,
    AccrualAdjustment,
    OwnerDrawReclass,
    CapitalizeAndDepreciate,
    AcceptDifference,
    AccountantSummary,
}

pub enum ProposalState {
    Proposed,
    Accepted,
    Rejected { reason: String },
    Superseded,
    Expired,
}

pub enum DispositionRule {
    RequiresHumanReview,
    // reserved for post-v1 (kanso_contracts MUST refuse non-RequiresHumanReview in v1):
    AutoPromoteIfValidationClean,
    AutoPromoteIfValidationCleanAndAmountUnder { amount_cents: u64 },
    AutoPromoteIfKindIn(Vec<ProposalKind>),
}
```

Rules:

- `proposals/<year>.jsonl` is append-only; state transitions are new
  records (or supersession), never in-place mutations
- `validation_result` is Kanso-written; agent input is ignored on this
  field
- `journal_projection` is required for posting-bearing kinds (rule
  `agent.proposal.journal_projection_required_for_kind`); Kanso projects
  it deterministically and embeds it
- `disposition_rule = RequiresHumanReview` is the only legal value in v1
  (rule `agent.policy.disposition_not_supported_in_v1`)
- acceptance writes a `ReviewDecision` with `from_proposal:
  <AgentProposalId>` lineage; the posting engine consumes the
  `ReviewDecision`, never the proposal directly
- rejection requires a non-empty `reason`

## Match Types

```rust
pub enum MatchStatus {
    Matched,
    MissingEvidence,
    AwaitingStatement,
    Ambiguous,
    DuplicateSuspected,
    Suspicious,
}

pub enum ConfidenceFactorKind {
    AmountExact,
    AmountNear,
    DateExact,
    DateNear,
    VendorSimilarity,
    DocumentType,
    DuplicatePressure,
    UserDecision,
    CurrencyMismatch,         // lowers confidence; surfaces as Suspicious
    EnsembleAgreement,        // two engines agree on a value; confidence → 100
    EnsembleNormalizedAgreement, // agree after normalization; confidence → 95
    EnsembleDisagreement,     // engines disagree; candidates shown in drawer
    ReceiptBoundary,          // confidence that a page cluster is one receipt
}

pub struct ConfidenceFactor {
    pub kind: ConfidenceFactorKind,
    pub score_delta: i32,
    pub explanation: String,
    pub rule_id: RuleId,
}
```

`MissingEvidence` is the transaction-side objective state (no receipt found).
`AwaitingStatement` is the evidence-side objective state (no transaction found yet).
Both are non-errors. Policy decides whether either requires action.

Currency mismatch does not create a new status; it makes the candidate `Suspicious`
with `ConfidenceFactorKind::CurrencyMismatch`.

Confidence must be explainable from factors.

## Registry Shape

Contracts expose:

- keyed lookup for engine/runtime
- ordered slices for deterministic exports and tests

Expected pattern:

```rust
pub static RULE_BINDINGS: phf::Map<&'static str, RuleBinding>;
pub const ALL_RULE_IDS: &[RuleId];
pub const ALL_EXPORT_SPECS: &[ExportSpecId];
pub const ALL_HELP_TOPICS: &[HelpTopic];
```

Use simple static definitions first. Avoid build scripts until real complexity
requires them.

## Help And Recovery Registry

Help is compiled contract data.

Expected pattern:

```rust
pub static RULE_EXPLANATIONS: phf::Map<&'static str, RuleExplanation>;

pub static COMMAND_DESCRIPTORS: phf::Map<&'static str, CommandDescriptor>;

```

Rules:

- every reachable `RuleId` has a `RuleExplanation`
- every recoverable validator/runtime error has a `RecoveryHint`
- every user/agent-facing command has a `CommandDescriptor`
- every served Kanso Interface tool has a `ToolHelpDescriptor`
- every example used by docs, prompts, MCP help, or conformance comes from
  `ALL_EXAMPLE_RECIPES`
- `kanso dev export-contracts --check` fails when generated help, doctor,
  prompt, example, or MCP artifacts are stale

## Generated Output Boundary

The contract crate is the upstream source for:

- TypeScript raw bindings
- JSON schemas
- provider prompt schemas
- export schemas
- contract docs
- example fixtures
- generated CLI help
- generated MCP help
- generated doctor recovery
- generated prompt fragments
- generated public examples

Generated output must not become an authoring source.

## Definition of Done

The type system is sufficient when MVP contracts can be implemented without new
semantic structures invented in validators, runtime, prompts, UI, or exporters.
