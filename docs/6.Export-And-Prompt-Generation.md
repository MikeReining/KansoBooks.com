# KansoBooks Export and Prompt Generation

**Status:** Canonical / Binding

## Purpose

Contracts generate downstream truth for:

- TypeScript bindings
- JSON schemas
- OCR/LLM prompt blocks
- generated help docs
- doctor/recovery metadata
- MCP help schemas
- export formats
- evidence-policy summaries
- human-readable contract summaries
- test fixtures

Docs and prompts must not become parallel semantic owners.

## Core Decision

Semantic outputs are generated views over Rust contracts.

Handwritten text is allowed for:

- product framing
- consent copy
- UI tone
- broad guardrails

Handwritten text is not allowed to define:

- financial invariants
- schema fields
- statuses
- confidence semantics
- evidence-policy requirements
- provider response shapes
- export column meaning
- help topics
- recovery/fix behavior
- prompt repair instructions

## Generated Surfaces

### TypeScript Bindings

Generated into:

```text
apps/desktop/src/types/generated/
```

Rules:

- raw IPC/domain bindings come from Rust
- UI may define curated view models only
- generated files are never edited by hand

### JSON Schemas

Generated for:

- provider requests
- provider responses
- extraction outputs
- export metadata
- evidence-policy metadata

Provider responses must validate before acceptance.

### Prompt Blocks

Generated prompt blocks include:

- extraction schema
- field descriptions
- output-only JSON requirement
- uncertainty handling
- prohibited inference rules
- repair instructions derived from rule/recovery metadata
- tool-use instructions derived from Kanso Interface descriptors

Prompt blocks must carry schema IDs or rule references where practical.

### Help And Recovery Artifacts

Generated help artifacts include:

- CLI help spec
- Kanso Interface help bundle
- doctor explanation map
- rule explanation map
- tool explanation map
- format reference
- validator-backed examples
- prompt fragments

Rules:

- help/recovery artifacts are generated from contracts and rule bindings
- doctor output cites generated recovery metadata
- examples render only from validator-backed recipes
- generated prompt fragments may instruct agents how to recover, but may not
  invent schema fields, tools, permissions, rule IDs, or accounting meaning

### Export Specs

Generated/exported specs define:

- columns/sections
- sorting
- readiness rules
- unresolved-finding policy
- active evidence policy and version
- redaction policy
- reproducibility metadata

V1 period-close adds the following export surfaces, each with a contract-owned
projection spec (in `report.rs`):

| Output | Projection source | Determinism requirement |
|---|---|---|
| Income Statement | journal — revenue and expense accounts, filtered to period | same journal → byte-identical output |
| Balance Sheet | journal — all accounts, as-of period end; must satisfy A = L + E | same journal → byte-identical output |
| General Ledger | journal — every line, chronological, with running account balances | same journal → byte-identical output |
| Trial Balance | journal — per-account Σ debit / Σ credit; must balance | same journal → byte-identical output; validator confirms balance |
| Reconciliation Summary | journal + statement manifests | same inputs → byte-identical output |
| Decisions Log | `decisions/<year>.jsonl` filtered to period | same decisions → byte-identical output |
| Evidence Index | evidence + transactions | same state → byte-identical output |
| Audit-Ready Package | bundle of above + Kanso Format snapshot + README + CHECKSUMS | same state → byte-identical bundle; sha256 manifest required |

Rules:

- no report may be generated if `close_gate.condition_not_met` findings exist
- the audit-ready package is the only export that packages the Kanso Format
  folder snapshot; point exports do not bundle raw source files
- re-running any export on the same closed period state MUST produce
  byte-identical artifacts (reproducibility is a validator-enforced invariant)

### Human Markdown

Contract summaries may be generated for internal docs and agent context.

They must remain concise and rule-ID traceable.

## Provider Prompt Rule

Prompts may ask a model to fill a schema.

Prompts may not ask a model to decide final financial truth.

Bad:

```text
Decide whether this transaction is valid and ready for taxes.
```

Good:

```text
Extract candidate receipt fields into this JSON schema. If uncertain, set the
field confidence low and include the source text.
```

## Export Readiness

Exports must run through readiness validation.

Rules:

- fatal findings block export
- unresolved review items must be represented honestly
- every exported match status comes from contract/review state
- every exported policy result comes from active policy evaluation
- export output records the contract version and source import batch

## Determinism

Generated outputs must be deterministic:

- stable ordering
- stable formatting
- stable schema IDs
- stable snapshots for same source

CI should fail when generated artifacts are stale.

## Adding a Contract Field

Canonical workflow:

1. add/change Rust contract
2. add rule binding and examples
3. update validator
4. regenerate TypeScript/schema/help/doctor/prompt/export outputs
5. run artifact check
6. run contract/validator/export tests

## Definition of Done

Export/prompt generation is correct when every semantic statement in generated
outputs traces back to contracts and no prompt/export file contains independent
financial truth.
