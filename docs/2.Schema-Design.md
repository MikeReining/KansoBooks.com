# KansoBooks Contract Schema Design

**Status:** Canonical / Binding
**Authority:** Subordinate to `Docs/Naming.md` for type names. The
work-unit type is `BooksPeriod` (replacing the legacy `Report` name);
`ReportOutput` is the family for generated financial outputs (P&L, BS,
GL, TB, etc.). The Kanso Interface / MCP coworker surface adds `AgentProposal`,
`agent_policy`, `mcp_tool_descriptor`, `mcp_manifest`, `mcp_error`, and
`agent_memory` per `Docs/MCPSurfaceModel.md`. Help and recovery surfaces add
`help_topic`, `rule_explanation`, `recovery_hint`, `fix_command`,
`example_recipe`, `prompt_fragment`, and `help_artifact_manifest` per
`Docs/HelpAndRecoveryModel.md`.

## Purpose

Define the minimum schema needed to drive:

- semantic validation
- runtime enforcement
- SQLite storage
- generated TypeScript bindings
- OCR/LLM JSON schemas
- exports
- GUI raw contracts
- contract-derived tests

If a static rule cannot be represented by this schema, the schema is
incomplete.

## Design Principles

- Contracts describe semantics, not prose.
- Financial fields are typed, not string bags.
- New rules are data plus generic validator logic where possible.
- Schemas preserve lineage from raw source to exported output.
- Generated outputs are downstream views.
- AI/provider schemas are derived from contracts.
- MVP avoids ledger posting but reserves ledger invariants.

## Money Model

Required shape:

```rust
pub struct Money {
    pub minor_units: i64,
    pub currency: CurrencyCode,
}
```

Rules:

- no floats
- currency required on every `Money` instance; hardcoded defaults forbidden
- original text may be preserved separately
- arithmetic only across matching currencies unless a later FX contract exists
- original currency is preserved and never overwritten; conversion is an added
  interpretation layer that lives alongside the original, not replacing it
- currency mismatches between evidence and transaction surface as `Suspicious`
  with `ConfidenceFactorKind::CurrencyMismatch`; no auto-conversion in MVP

## BooksPeriod

(Replaces the legacy `Report` work-unit type per `Docs/Naming.md`.)

Every import, evidence item, and review decision is scoped to a
`BooksPeriod`.

Minimum fields:

- `id`
- `display_name`
- `base_currency: Option<CurrencyCode>`
- `connected_expenses_folder: Option<String>`
- `connected_statements_folder: Option<String>`
- `extraction_strategy: Option<ExtractionStrategy>`
- `status: BooksPeriodStatus`
- `created_at`

Rules:

- `base_currency` is optional; if absent it is inferred lazily from the first
  imported statement and recorded as an `AuditEvent` of kind
  `books_period.base_currency_inferred`
- if set explicitly later, prior statement and receipt currencies are preserved;
  conversion becomes an interpretation layer, not a mutation
- a `BooksPeriod` may span multiple statement import batches and multiple
  date ranges
- a receipt without a matching transaction in the current imports is valid;
  its status is `AwaitingStatement`, not an error
- `status` follows the `BooksPeriodStatus` lifecycle per
  `Docs/BooksPeriod.md`: `draft` → `in_review` → `ready_to_close` →
  `closed` → optionally `reopened`. The transition to `closed` requires
  the close-gate evaluator to pass per `Docs/AccountingModel.md`.

- `IncomeStatementOutput`
- `BalanceSheetOutput`
- `GeneralLedgerOutput`
- `TrialBalanceOutput`
- `ReconciliationOutput`
- `DecisionsLogOutput`
- `EvidenceIndexOutput`
- `CloseReadinessOutput`

Each `ReportOutput` carries: `kind`, `books_period_id`, `format`

- `books_period_id`
- `entries: Vec<PackageEntry>` where `PackageEntry` is `{relative_path,

## AgentProposal

(Per `Docs/MCPSurfaceModel.md`. The universal mutation envelope produced
by MCP write tools. Append-only; lives in `proposals/<year>.jsonl`.)

Minimum fields:

- `id: AgentProposalId`
- `books_period_id: BooksPeriodId`
- `session_id: AgentSessionId`
- `agent_client: AgentClient` — `Claude` | `Cursor` | `Codex` |
  `GenericMcp` | `Other(String)`
- `proposal_kind: ProposalKind` — closed enum. v1 set:
  `change_category`, `pair_transfer`, `mark_personal`, `attach_evidence`,
  `post_transaction`, `accrual_adjustment`, `owner_draw_reclass`,
  `capitalize_and_depreciate`, `accept_difference`, `accountant_summary`
- `subject: ProposalSubject` — typed reference to the subject (transaction
  ID, statement ID, evidence ID, books-period ID, account pair, etc.)
- `payload: ProposalPayload` — the proposed change shape. For
  posting-bearing kinds, `payload` may include `suggested_lines`
  (debit/credit pairs) which Kanso records but does not consume directly
- `citations: Vec<Citation>` — references to specific source files,
  evidence IDs, transaction IDs, or `accounts.yaml` entries the agent
  used as evidence
- `validation_result: ValidationResult` — Kanso-written. Embeds the same
  `Findings` shape any other validator produces, scoped to this proposal
- `journal_projection: Option<JournalProjection>` — Kanso-written. Present
  only for posting-bearing kinds. Embeds the projected debit/credit lines
  Kanso would post if the proposal were accepted exactly as drafted
- `disposition_rule: DispositionRule` — v1 accepts exactly one value:
  `RequiresHumanReview`. The contract reserves `auto_promote_*` variants
  but `kanso_contracts` MUST refuse any non-`RequiresHumanReview` value
  in v1
- `state: ProposalState` — `Proposed` | `Accepted` | `Rejected` |
  `Superseded` | `Expired`
- `from_proposal: Option<AgentProposalId>` — supersession lineage
- `created_at: String`
- `created_by_agent_label: String` — what the user sees ("Claude
  Cowork", "Cursor agent", etc.)

Rules:

- `proposals/<year>.jsonl` is append-only. State transitions are recorded
  as new lines (or via `supersedes`); records never mutate in place.
- Acceptance writes a `ReviewDecision` to `decisions/<year>.jsonl` with
  `from_proposal: <AgentProposalId>` lineage; the posting engine consumes
  that `ReviewDecision`. Kanso never posts from the `AgentProposal`
  directly.
- Rejection requires a non-empty `reason` field on the rejection record.
- Every state transition emits an audit event per the audit taxonomy
  below.

## JournalEntryProposal (view, not storage)

A `JournalEntryProposal` is a presentation-layer view over an
`AgentProposal` whose `proposal_kind` is posting-bearing. It is not a
separate storage primitive. The view exposes:

- plain-language summary of what changes
- Kanso-projected debit/credit lines (from `journal_projection`)
- agent-suggested lines (from `payload.suggested_lines`) with diff
  highlighting against the projection
- citations and confidence factors
- accept / edit / reject actions

Only the Kanso projection can become a posted journal entry. The agent's
`suggested_lines` are recorded for audit and trust but are advisory only.

## AgentPolicy (`policies/agents.yaml`)

(Per `Docs/MCPSurfaceModel.md`. Schema lives in the contract layer; the
on-disk YAML is deserialized into the `AgentPolicy` Rust type.)

Minimum shape:

- `version: u32`
- `defaults: AgentDefaults` — `cloud_consent: bool`, `max_tools_per_session:
  u32`, `default_grant_for_read_tools: bool`
- `grants: Vec<AgentGrant>` where `AgentGrant` is:
  - `tool: McpToolName`
  - `granted: bool`
  - `scope: GrantScope` — `ActiveBooksPeriod` | `AnyBooksPeriod` |
    `SpecificBooksPeriods(Vec<BooksPeriodId>)`
  - `constraints: Vec<AgentConstraint>` — `RequireCloudConsent`,
    `RequireUserConfirmationPerCall`, `MaxAmountCents(u64)` (proposal
    cap), `OnlyKindsIn(Vec<ProposalKind>)`, etc.
  - `disposition: DispositionRule` (always `RequiresHumanReview` in v1)
  - `granted_at`, `granted_by` (currently always `User`)
- `revoked: Vec<AgentGrantRevocation>` — append-only revocation log

Rules:

- read tools default-granted in shipped templates
- write tools require explicit `granted: true`
- grant edits emit `AgentPolicyChanged` audit events
- the validator MUST refuse any policy that violates the v1 disposition
  lock

- `dry_run_supported: bool`
- `deprecation: Option<McpDeprecation>`

Minimum shape:

- `interface_version`
- `tools: Vec<McpToolDescriptor>`

- `cli_parity_command`

Generated discovery view. It is not hand-authored by prompts or product copy.

Minimum shape:

- `kanso_interface_version`
- `supported_format_versions`
- `transport`
- `scope`
- `features`
- `tools: Vec<McpToolDescriptor>`

Rules:

Uniform Kanso Interface error envelope.

Minimum shape:

- `code`
- `rule_id: Option<RuleId>` — present for validator/policy failures; null for
  runtime/environment failures that are not static rules
- `severity`
- `human_explanation`
- `suggested_fix`
- `citations`
- `net_user_actions_impact`
- `retryable`
- `trace_id: McpTraceId`

Rules:

- contract-known failures without `rule_id` are invalid

- `human_explanation` and `suggested_fix` come from contract/runtime error

Scoped memory primitive for agents.

- `id: AgentMemoryId`
- `scope: AgentMemoryScope` — default `(BooksPeriodId, skill_id, session_id)`

- `body` — kind-specific typed payload
- `citations`
- `created_at`
- `expires_at`
- `digest`
- `supersedes: Option<AgentMemoryId>`

Rules:

- cross-folder memory is forbidden
- cross-period memory requires explicit grant

## Document and Evidence

`ExtractedDocument` is provider/local extraction output.

`EvidenceDoc` is validator-accepted evidence.

Minimum fields:

- `id`
- `source_file_id`
- `document_type`
- `merchant_raw`
- `merchant_normalized`
- `transaction_date`
- `total_amount`
- `tax_amount`
- `currency`
- `confidence`
- `extraction_method`
- `provider_id`
- `provider_version`
- `field_lineage`
- `page_range: Option<PageRange>` — start and end page (inclusive, 1-based) within
  the source file; present when the source is a multi-page PDF; a single-page receipt
  uses `start == end`
- `description: Option<String>` — free-text description or comment from the source
  (e.g., the `Comment` field from an Expensify CSV)
- `category_proposed: Option<String>` — category label from the source as a proposal
  only; not financial truth; carries no semantic effect on matching or policy
- `tag_proposed: Option<String>` — tag label from the source, same rules as
  `category_proposed`
- `external_evidence_url: Option<String>` — URL of the original receipt on an
  external service (e.g., Expensify); stored passively; never fetched by Kanso
- `field_confidences: Option<FieldConfidences>` — per-field confidence integer (0–100)
  for merchant, date, total, currency, and tax when the provider returns field-level
  signal

Rules:

- provider output must validate before becoming evidence
- low-confidence extraction remains reviewable
- every accepted field should point to source location where available
- `category_proposed` and `tag_proposed` are proposal metadata only; they MUST NOT
  influence match status, policy severity, or export truth
- one `SourceFile` may produce N `ExtractedDocument` rows (multi-receipt PDF);
  each row carries its own `page_range`
- an `EvidenceDoc` may carry more than one `source_file_id` when CSV and PDF sources
  for the same expense are merged; lineage carries both sources

## Matching

Match candidate fields:

- `id`
- `bank_transaction_id` — present on transaction-side candidates
- `evidence_doc_id` — present on evidence-side candidates (`awaiting_statement`)
- `evidence_doc_ids` — linked evidence on transaction-side candidates
- `status`
- `confidence`
- `confidence_factors`
- `rule_ids`
- `created_at`

Allowed MVP statuses:

- `matched` — one high-confidence evidence link for a transaction
- `missing_evidence` — transaction exists, no plausible receipt/document found
- `awaiting_statement` — evidence exists, no matching transaction imported yet;
  valid and non-blocking under Lean policy; user copy: "Waiting for statement."
- `ambiguous` — multiple plausible evidence links
- `duplicate_suspected` — transaction or evidence appears duplicated
- `suspicious` — amount, date, vendor, currency mismatch, refund, or pattern anomaly

`missing_evidence` and `awaiting_statement` are symmetric objective states, not errors.
Policy decides whether either requires action.

Currency mismatch between evidence and transaction does not produce a new status.
It produces `status = Suspicious` with `ConfidenceFactorKind::CurrencyMismatch` and
rule ID `matching.currency_mismatch_review`.

Review may add `reviewed` state through `ReviewDecision`, not by mutating the
candidate into unexplained truth.

## Validation Finding

Canonical shape:

```rust
pub struct ValidationFinding {
    pub rule_id: RuleId,
    pub severity: FindingSeverity,
    pub message: String,
    pub location: FindingLocation,
    pub subject: Option<String>,
}
```

Findings must answer:

- what is wrong
- where it is wrong
- which rule was violated
- what state is blocked or degraded

## Journal Entry

Minimum fields:

- `id` — stable journal entry ID
- `ts` — ISO 8601 timestamp
- `period` — the period the entry belongs to (e.g. `2026-Q1`, `2026`)
- `memo` — human-readable description
- `triggered_by_decision` — reference to the `ReviewDecisionId` or
  format-layer decision that caused the entry
- `auto_reverse` — date of automatic reversing entry, or `null`
- `reverses_entry` — for auto-generated reversals, the entry being reversed
- `lines` — ordered list of `JournalLine` records

Each `JournalLine`:

- `account` — account ID from `accounts.yaml`
- `debit` — `Money` or null
- `credit` — `Money` or null

Rules:

- exactly one of `debit` or `credit` is non-null per line
- Σ debits = Σ credits is enforced at write time; violation is a static
  contract error
- entries are append-only once posted
- corrections are reversing entries, not edits
- `triggered_by_decision` is mandatory; no anonymous posting

## Chart of Accounts

Minimum fields per account: `id`, `name`, `type`, `normal_balance`,
`report_section`. Full structural model in `Docs/AccountingModel.md`.

Rules:

- duplicate IDs are a contract error
- `normal_balance` must be consistent with `type`
- accounts referenced by posted entries may not be deleted (archived only)
- system accounts required by posting rules may not be absent

## Adjustment Contract

Minimum fields:

- `decision_id` — the decision that owns this adjustment
- `kind` — one of the v1 six (see `Docs/AccountingModel.md`)
- `period` — the period being closed
- `value` — kind-specific payload (amount, accounts, method, useful-life
  for `capitalize_and_depreciate`)
- `auto_reverse` — date, or null for permanent reclassifications
- `journal_entry_ids` — the entries this adjustment produces

Rules:

- only the v1 adjustment kinds are contract-defined; others are forbidden
- `capitalize_and_depreciate` must carry `useful_life_years`, `method`, and
  `half_year_convention`; the validator MUST verify the posted depreciation
  math matches the declared method
- auto-reversals fire as their own entries on the named date; the trigger is
  the original adjustment decision

## Reconciliation Contract

Minimum fields per source account per period:

- `account_id`
- `period`
- `opening_balance` — `Money`
- `expected_closing` — `Money` (computed from posted inflows/outflows)
- `statement_closing` — `Money` (from statement manifest)
- `difference` — `Money` (expected − statement)
- `status` — `Tied` | `Difference` | `AcceptedWithDifference`
- `accept_difference_decision_id` — non-null when `AcceptedWithDifference`

Rules:

- `status = Tied` iff `difference.minor_units == 0`
- `status = AcceptedWithDifference` requires a valid `accept_difference`
  decision with a reason
- a non-tied, non-accepted account blocks the close gate
- no silent rounding; no plug entries

## Export Requirements

Every export spec declares:

- input state requirements
- included columns/sections
- sorting
- redaction policy
- unresolved-finding policy
- active evidence policy and policy-version metadata
- reproducibility metadata

V1 export bundle includes:

- `transactions.csv` — status, currency, confidence, evidence link per row
- `review_report.csv` — issues, certainty gradients, reason factors
- `audit_log.jsonl` — all `AuditEvent` records for the `BooksPeriod`,
  in order
- `policy.json` — active `EvidencePolicy` and version
- `currencies.json` — base currency, statement currencies, receipt currencies,
  mismatches (if any)
- `MANIFEST.json` — index with sha256 of each artifact for downstream verification

V1 period-close export bundle additionally includes:

- `income-statement.{md,pdf}` — projected from journal
- `balance-sheet.{md,pdf}` — projected from journal + opening balances
- `general-ledger.csv` — all journal lines in chronological order
- `trial-balance.csv` — per-account Σ debit / Σ credit; MUST balance
- `reconciliation.md` — per source account: opening, expected close,
  statement close, difference, acceptance
- `decisions.md` — human-readable rendering of the decisions log for the period
- `evidence-index.md` — every receipt and statement linked to the period
- `audit-package.zip` — bundle of above plus Kanso Format folder snapshot plus
  `README.md` and `CHECKSUMS.txt`

Re-running export on the same reviewed state must produce byte-identical artifacts.

## Definition of Done

Schema design is sufficient when every MVP import, match, review, audit, and
export rule can be represented without handwritten parallel semantics.
